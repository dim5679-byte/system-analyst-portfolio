# Принципы оформления портфолио

## 1. Портфолио должно демонстрировать работу аналитика

Основная цель репозитория — показать не количество файлов, а умение системно описывать решение.

Каждый артефакт должен отвечать на конкретный вопрос проекта и быть связан с другими документами.

---

## 2. Связность документации

Основные артефакты должны формировать логическую цепочку:

`Requirements → BPMN → ERD → SQL → API → UML → Architecture`

Из документа должно быть понятно, как он связан с остальной системой.

---

## 3. Один источник истины

Не следует дублировать одну и ту же информацию в нескольких документах без необходимости.

Если информация уже подробно описана в одном разделе, в другом лучше использовать ссылку.

Например:

- структура БД — в ERD и SQL;
- API-контракты — в OpenAPI;
- бизнес-правила — в Requirements;
- последовательность взаимодействия компонентов — в UML.

---

## 4. Простота важнее избыточности

Документация должна быть достаточно подробной для понимания решения, но не перегруженной.

Не следует добавлять:

- лишние технологии;
- неиспользуемые компоненты;
- микросервисы без необходимости;
- сложные архитектурные шаблоны только ради демонстрации.

---

## 5. Все заявленные технологии должны подтверждаться артефактами

Если технология указана в README, в репозитории должен быть пример её применения.

Например:

- `SQL` → SQL-файлы;
- `OpenAPI` → YAML-спецификация;
- `BPMN` → BPMN-диаграммы;
- `UML` → Sequence Diagrams;
- `ERD` → модель данных.

---

## 6. Документация должна быть понятна без устного объяснения

HR или технический специалист должен иметь возможность открыть репозиторий и самостоятельно понять:

- что это за система;
- какая задача решается;
- какие сценарии реализованы;
- где находятся ключевые документы;
- как связаны данные, API и процессы.

---

## 7. Основной язык — русский

Поскольку портфолио ориентировано на поиск работы в России, пояснения и проектная документация оформляются на русском языке.

Общепринятые технические термины сохраняются на английском:

- REST API;
- OpenAPI;
- SQL;
- PostgreSQL;
- BPMN;
- UML;
- ERD;
- JWT;
- Backend;
- Mobile App.

---

## 8. Единый стиль

Во всех разделах используются:

- единая структура заголовков;
- одинаковый формат статусов;
- единые названия компонентов;
- одинаковые правила именования файлов;
- относительные ссылки внутри репозитория.

---

## 9. Исходник и превью диаграммы

Для диаграмм рекомендуется хранить:

- `.drawio` — редактируемый исходник;
- `.png` — превью для просмотра на GitHub.

Это позволяет одновременно показать результат и предоставить исходный файл.

---

## 10. Репозиторий должен выглядеть завершённым

Перед публикацией необходимо исключить:

- временные файлы;
- backup-файлы;
- `final2`, `new`, `last` в именах;
- неработающие ссылки;
- устаревшие статусы `В работе`;
- пустые разделы без пояснения.
